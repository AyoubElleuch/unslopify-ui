# Feedback

## Sound feedback

- Never add sound on/off buttons or other sound controls. Use sound only when requested and exercise judgment: choose a very small number of meaningful interactions where audio reinforces feedback, rather than playing on every action. Consider frequency and context; if a cue becomes repetitive or distracting, omit it.
- Possible uses include confirming an important completed action, or a drag-and-drop interaction: a short pickup cue when dragging begins and a distinct drop cue only after a valid drop. These are examples, not a mandatory or exhaustive list. Never play continuously during dragging, on every drag-over event, or for routine navigation, hover, typing, focus or opening menus.
- Keep cues short, quiet and distinct. A simple sine wave with a quick fade-in and fade-out avoids clicks; for example, pickup at 440 Hz and drop at 587 Hz for approximately 100 ms. Treat pitches and gain as starting choices, not loudness guarantees. Honor device volume and browser audio policies; handle unavailable or blocked audio without breaking the interaction. Never make sound the only indication of an action or state; preserve visual and accessible feedback. Test repetition, cancelled or invalid drops, shared environments and real devices.

## Dialog dismissal and destructive actions

- For ordinary modal dialogs and drawers, clicking the dimmed backdrop dismisses the window. Only dismiss if both pointer press and release happen on the backdrop, so dragging from inside does not accidentally close it. A click inside the window or on its open popovers must not close it. Escape and a clearly labeled close or cancel control must also work, and focus should return to the opener. Keep modal focus and background interaction correctly managed.
- If dismissing would discard meaningful unsaved changes, preserve the draft or ask the user to confirm discarding it. Critical or irreversible confirmation flows may require an explicit decision instead of backdrop dismissal; explain the reason and always provide a clear keyboard-accessible exit.
- Make destructive actions recognizable and readable: use an explicit label such as “Delete task”, a legible 14px label, appropriate danger color with at least 4.5:1 text contrast, and a 40px minimum desktop target (44px for touch). Give it a clear hover and keyboard focus state. Place it separately from the primary save action; confirm destructive operations when their consequences or irreversibility warrant it. Test the action, focus, reduced-motion, long labels and narrow screens.

## Action feedback and error handling

- Inventory every visible control, including dynamically generated rows, menus, keyboard actions and empty states. Each enabled control must perform its stated action or explain clearly what is unavailable. Remove decorative elements that look actionable; do not silently leave enabled controls inert.
- For unfinished functionality, show a concise, accessible message naming the action and stating that it is unavailable or a demo. Do not claim that data was saved, a message was sent, or an operation succeeded unless it actually did. Do not intercept working links, form controls, native disclosures or disabled controls with a blanket fallback.
- Validate input next to the affected field, preserve entered data on failure, and explain how to correct it. For operation failures, show an accessible, persistent or actionable error near the operation; use a polite status for short informational feedback and an alert for urgent errors. Keep critical errors visible until resolved or dismissed, and provide retry when safe.
- Handle expected failures at the operation boundary: network and server errors, timeouts, offline state, storage and permission failures, clipboard and downloads, missing or stale records, and rejected requests. Prevent duplicate submissions while pending; distinguish loading, success, empty, partial and failure states. Avoid exposing technical or sensitive details. Confirm success only after the operation completes, preserve unsaved input, and do not retry non-idempotent actions automatically. Log diagnostic details appropriately.
- Audit all routes and responsive states using mouse and keyboard; test success and failure paths, rejected permissions, unavailable storage, invalid data and repeated clicks. A global error handler is a last-resort notice, not a substitute for handling each operation.

## Errors and notifications

- **Choose the right location:** Show a field-specific validation error inline, directly below its control, so the user can see what to fix. For a failed submission affecting several fields, focus the first invalid field; for long or complex forms, an additional summary can link to the errors. Use a page-level message for an error that affects the whole form. A temporary notification is appropriate for a brief, noncritical event that does not need a field-specific correction.
- **Group the error with its field:** Start with **4–8px** from the control to the error, then **16–24px** from the end of the error to the next field or group. These are design defaults, not universal standards. The message belongs to the field above it, not the next one. If a grid or flex container supplies `gap`, do not add the same spacing again as margin. Let the group grow when text wraps, and restore normal spacing when the error clears.
- **Make errors useful:** State the problem and, where possible, the fix in plain language. Use readable text and contrast, not color alone; associate it programmatically with the control using `aria-describedby` and `aria-invalid`. Announce new errors appropriately, preserve labels and keyboard operation, and focus the first invalid control after submission. Avoid repeated disruptive announcements on every keystroke.
- **Choose notification placement in context:** Center top, center bottom, or a side can all work. Keep notifications visible at different viewport sizes without covering fields, actions, navigation, or other messages; stack multiple notifications predictably. Use a brief fade and/or small movement, and respect reduced-motion preferences. Announce status messages without moving focus.
- **Do not hide important errors:** A transient message must not be the only record of a field error, a critical failure, or an action the user still needs to take. Keep those messages visible until resolved or dismissed. Provide a dismissal control where appropriate and give users enough time to read temporary messages.
