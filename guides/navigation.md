# Navigation

## Breadcrumb navigation

- Show breadcrumbs only when they communicate a real location hierarchy and give access to parent destinations. Each ancestor must navigate to its actual parent; the current page is plain text marked `aria-current="page"`, not a link to itself. At the root, omit redundant ancestors and separators. Do not use breadcrumbs as a substitute for a back button or a record of browsing history.
- Use a labeled breadcrumb navigation landmark, clear sentence-case labels in the product's normal UI font (start at 14px / 20px), and a small, centered, decorative SVG chevron between items. Start with 4–8px gaps and compact padding; use a clear hover and keyboard-focus treatment. Do not let font styling, tiny text or excessive whitespace dominate the header. Truncate or wrap long labels deliberately without losing access to destinations; verify keyboard operation, narrow screens, zoom and the root state.

## Sidebar visual reference: Ember

For application sidebars, use the supplied Ember screenshot as a visual direction alongside the sizing and accessibility schema below. Adapt the design to the product and its own palette; do not copy the reference's black and gray colors by default.

- Arrange a compact brand row at the top. Search is optional: decide from the number and type of destinations, user tasks, and existing search locations; ask the user when its need or scope is unclear. A short, scannable menu rarely needs its own search. If the control searches records rather than navigation, label its scope and place it with those records or in an established global search, avoiding duplicates. A collapse control or keyboard shortcut hint belongs there only when the corresponding behavior exists.
- Separate the header from navigation with a subtle full-width divider. Omit generic labels such as “Navigation”; use a readable section label only when it distinguishes meaningful groups.
- Stack consistently aligned menu rows with a small outline SVG icon, a clear sentence-case label, and an optional trailing count or disclosure chevron when it communicates real information or behavior. Align icons, labels, and trailing elements consistently; leave comfortable space between rows.
- Mark the current destination with a restrained filled surface and brighter, slightly stronger text and icon. Choose either inset rounded rows or full-width rows extending across the sidebar for both hover and selected states; apply one style consistently within a sidebar. The selected fill may use a subtle border or gentle tonal shading, but no colored edge stripe, decorative dots, or separate icon background. Keep unselected items quiet but readable, and give hover and keyboard focus their own clear states.
- Keep the sidebar visually quiet: no redundant workspace card, promotional panel, fake controls, or filler copy. Keep a profile control when useful, and make overflow scroll without stretching the sidebar beyond the viewport.
- Treat the screenshot as inspiration, not a pixel specification: preserve readable contrast, appropriately sized navigation text, comfortable target sizes, keyboard access and the product's visual identity.

## Sidebar design schema

Use these as starting values, not universal standards. Adjust for the product, language, typeface, content and device, then verify the rendered interface. The NovaStage reference informs the restrained structure, not a shared color palette.

| Decision | Default and implementation |
| --- | --- |
| Content | Keep the product identity, frequently used navigation, meaningful section labels, and an account control when needed. Remove promotional cards, decorative statistics, repeated profile/workspace blocks and fake switchers. Show a workspace switcher only when people can actually switch workspaces; identity and account are distinct when both have a real purpose. Place operational summaries in the main view. |
| Account area | Follow the supplied NovaStage account-area reference: at the bottom of the sidebar, add a subtle full-width divider, then a horizontal identity row with a 28px avatar on the left and a two-line name and role (or other useful account detail) on the right. Start with 13px name text, 12px secondary text and a 10px avatar gap; keep both readable. Below, place a separate sign-out row with a 16px outline SVG centered optically beneath the avatar and its label aligned with the identity text; use a shared icon column and adjust for actual SVG artwork rather than relying only on bounding-box edges; no icon tile or decorative ellipsis. Follow the reference: the row is transparent by default, and hover fills the entire inset row with a subtle rounded surface and readable brighter text and icon. Animate the hover in and out briefly, preserve visible keyboard focus, and respect reduced motion. Start with a 36px pointer target and 44px touch target. Adapt colors to the product palette. Real sign-out must end the session; demos without authentication must say so. Check long names, narrow sidebars, zoom and internal sidebar scrolling. [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) sets a 24px minimum with exceptions. |
| Width and placement | Start around 232–256 CSS px for a simple desktop menu; measure the longest common label, icon, gaps, trailing controls and padding, then widen only as needed. Wider and resizable navigation may be appropriate for complex trees. Keep the sidebar within the viewport height. Allow vertical scrolling when content exceeds available height, including at zoom or short viewport heights; never cut off controls or leave the sidebar ending midway down a scrolled page. |
| Item geometry | For compact desktop menus, start around 36–40 px minimum row height, 8–12 px horizontal padding and no gap or vertical margin between adjacent rows, so hovered and selected backgrounds meet. Prefer at least 44 px height for touch and when the audience benefits from larger targets. Use min-height, not rigid height, so longer labels and user text spacing can grow. Indent nested items by about 16 px when nesting is needed. Aim for 44 × 44 px controls; WCAG AA target-size minimum is 24 × 24 px with specified exceptions, not a universal 44 px requirement. |
| Type and icons | Start with readable sentence-case labels around 14 px and 20 px line-height, regular/medium weight. A slightly smaller size such as 13–13.5 px can be considered for a compact desktop interface after verifying readability, contrast and zoom; avoid shrinking labels merely to fit; use 600 sparingly for the current item. Section labels can start at 13–14 px and must remain readable. Use consistent 16–20 px SVG icons only when helpful, with roughly 10–12 px between icon and text. Avoid icon background tiles and decorative dots. |
| Color and states | Derive surface, text, hover, selected, border and focus colors from the site's own palette. On dark surfaces choose light readable text; on light surfaces choose dark text. Test every text/background combination at 4.5:1 for normal text, and required non-text state and focus indicators at 3:1 against adjacent colors. Use a subtle filled selected row plus weight and programmatic current-page state; don't add a colored edge stripe. Hover, selected and keyboard focus must remain distinguishable, including without relying on color alone. |
| Responsive and interaction | At narrow widths collapse to an accessible overlay or use a genuinely usable compact navigation. Keep all destinations reachable. Use navigation landmarks, real links for navigation where routing allows, buttons for actions, descriptive labels, and aria-current for the active destination. Support keyboard focus, visible immediate focus feedback and reduced motion. |
| Verification | Inspect all destinations and states at desktop, narrow widths, short heights and 200% zoom; test long labels, many items, scroll, keyboard and focus, active item, account access and contrast in both themes. Remove filler before shrinking type. |

References: [Carbon side navigation specifications](https://www.carbondesignsystem.com/building-blocks/core/components/ui-shell-left-panel/specifications) (256 px panel, 14 px labels and a denser 32 px row), [Atlassian navigation layout](https://atlassian.design/components/navigation-system/layout) (resizable navigation and responsive overlays), [Atlassian navigation purpose](https://atlassian.design/components/navigation-system/migration-guide), [GOV.UK focus states](https://design-system.service.gov.uk/get-started/focus-states/), [Atlassian interaction motion](https://atlassian.design/components/primitives/pressable/usage), and [WCAG 2.2](https://www.w3.org/TR/WCAG22/) (contrast, focus, text spacing and target sizes). The 36–40 px desktop row and other values above are our design choices, not claims that the cited systems require them.

Account pattern references: [Carbon profile menus](https://www.carbondesignsystem.com/building-blocks/core/patterns/disclosures) group account and session actions, and its [UI shell example](https://labs.carbondesignsystem.com/?path=%2Fstory%2Freact_components-uishell--demo) includes a labeled log-out action with an icon. [GOV.UK service navigation](https://design-system.service.gov.uk/patterns/navigate-a-service/) emphasizes an easy route to account and sign-out. This project keeps sign-out directly below the name as requested; these examples do not prescribe that placement.

Search placement reference: [GOV.UK service navigation](https://design-system.service.gov.uk/patterns/navigate-a-service/) recommends identifying the scope of service search; [Atlassian navigation](https://atlassian.design/components/navigation-system/migration-guide) places its cross-app search in the top navigation. Neither makes sidebar search mandatory.
