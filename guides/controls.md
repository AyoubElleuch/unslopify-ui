# Controls

## Hover-state audit

- **Align the visible hover with the control:** Center an icon within the visual hover and focus surface, and align the entire control to the surrounding layout. Never push the artwork to one edge of a larger highlighted box just to align it with nearby text or numbers. If visual alignment and a generous hit target need different sizes, separate the centered visual surface from the larger clickable area, keeping both centered; check the actual hover and focus bounds at normal and touch sizes. Avoid redundant native title tooltips when an accessible name already identifies a familiar icon-only action.
- Inventory every interactive element and its actual states: navigation rows, icon buttons, links, text buttons, cards that act as controls, form controls, menus, table actions, disclosures and drag targets. Hover must match the control's shape and role: use a restrained fill for a row or icon button, a suitable border/fill for a field or button, and an underline or color change for a link. Avoid unexpected rectangular outlines, default borders, oversized tiles, layout shifts and clipping. Noninteractive content should not imply a click action.
- Design default, hover, pressed, selected, disabled and keyboard-focus states together; check combinations such as selected plus hover and focused plus hover. Keep the selected destination identifiable. Pointer hover and keyboard focus are different: use `:focus-visible` for a clear, appropriately shaped keyboard indicator rather than a permanent hover outline; never remove the only visible keyboard focus indicator, and provide a system-color outline in forced-colors mode.
- Keep text and necessary icons readable against their actual hover surface (ordinary text at least 4.5:1, necessary non-text indicators generally 3:1); check neighboring surfaces and intermediate transition colors too. Keep the visible cue within its intended bounds and preserve a comfortable hit target even if the icon is small.
- Transition appropriate colors over roughly 120–180ms in both directions, without animating geometry or delaying focus. Disable nonessential motion for reduced-motion preferences; ensure touch and keyboard users can use every action without hovering. Check every state at normal and narrow widths, with zoom, long labels, multiple themes and real pointer/keyboard input. Do not claim an audit is complete based solely on CSS inspection.

## Button visibility and sizing

- Inventory every enabled action, including add and delete controls, table actions, icon-only buttons, secondary links styled as buttons, and dynamically generated or empty-state actions. An enabled control must be discoverable in its resting state, not only on hover. Use a meaningful label or recognizable SVG with an accessible name, readable contrast and a clear interactive treatment. Never rely on color alone to communicate a destructive action.
- Choose emphasis by task: give the main action a prominent treatment; use a quieter but readable treatment for secondary actions; use an explicit danger label and color for destructive actions. If actions are peers in a group, align their heights and type. Compact contextual actions can be visually smaller when hierarchy calls for it, but must remain legible and have a usable target. Start text actions at 14px/20px and standalone icon targets at 40px on desktop and 44px for touch when practical. Do not shrink essential text to fit.
- Check the actual foreground/background pairing: ordinary text needs at least 4.5:1 contrast, and essential icons and necessary control boundaries need 3:1 against adjacent colors (subject to WCAG exceptions). Check resting, hover and focus states; keep the label or icon visible throughout transitions. Provide distinct keyboard focus and verify long labels, disabled states, responsive layouts and touch input. Apply judgment to role and context rather than making all buttons equally prominent or equally large.

## Button color, type and hover decision map

1. **Choose the role and fill.** Use the strongest action color sparingly for the primary action. Use a quieter surface or outline for secondary actions. Start with the supplied palette's appropriate action tone; its name or position in the palette does not establish whether it is readable. Evaluate the actual rendered fill against its surrounding surface; where the boundary is needed to identify the button, it must have at least 3:1 contrast against adjacent colors. If the fill does not provide it, add a contrasting boundary or change the fill.
2. **Choose the label by calculation.** For each candidate foreground, compute WCAG contrast against the actual opaque/composited button fill using relative luminance and `(lighter + 0.05) / (darker + 0.05)`. Start with the palette's darkest and lightest neutral; choose a candidate meeting at least 4.5:1 for ordinary button text, preferring more headroom. If neither passes, try black and white; if the result conflicts with the intended design, adjust the button tone and test again. Do not assume the primary or complementary swatch is a safe text color. At 24px regular or approximately 18.67px bold (700), WCAG permits 3:1 for large text, but keep the 4.5:1 project target when possible. Do not round up failures.
3. **Choose size and weight by role.** Start compact desktop buttons at 14px/20px, weight 500–600, and around 36–40px high; standard buttons at 14–16px/20–24px, weight 500–600, and 44px high; large promotional actions at 16–18px/24px, weight 600, and at least 48px high. These are project defaults, not universal thresholds. Match adjacent controls, accommodate wrapping and localization, and use 44px targets for touch where practical. Choose a genuine font weight and inspect its actual rendering; small text does not become readable merely by making it heavy, and a larger label does not automatically need bolder text.
4. **Build and test states as pairs.** Define explicit fill, label, icon, border and focus colors for default, hover, pressed and focus-visible states. For hover start with a subtle related lighter or darker fill, keeping the same foreground color. Measure label/fill contrast for every state; required icons and focus/boundary indicators generally need 3:1 against their adjacent colors. If hover fails, reduce the tone change or choose a new fill/foreground pair that passes in both states; do not fade text opacity. Disabled controls have WCAG contrast exceptions but should still be distinguishable and readable when practical.
5. **Animate without losing contrast.** Transition background and border over about 120–180ms ease-out in both directions; keep the text and icon color fixed across the transition when possible. Check the actual composited intermediate colors, not only the endpoints: for sRGB interpolation, sample at 1% intervals with contrast headroom, and review gradients, transparency and overlapping layers separately. If a sampled state fails, shorten the color change or use a different passing pair; if no single foreground works throughout, change the design rather than cross-fading through illegible colors. Keep focus immediate and visible. Disable nonessential transitions for reduced motion, and do not rely on hover to reveal a required action.

Examples from the revised sites: white on `#17243B` is about 15.53:1 and on its `#263C5C` hover is 11.15:1; dark `#211A34` on `#A496CD` is 6.20:1 and on `#9181C2` hover is 4.85:1. These are examples, not a mandatory palette. Validate actual rendered states and browser interpolation before release.

Sources: [Carbon button specifications](https://www.carbondesignsystem.com/building-blocks/core/components/button/specifications), [Atlassian button motion](https://atlassian.design/components/primitives/pressable/usage), [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum), and [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast). The timing and sizes above are project starting choices, not requirements from those systems.

## Icon groups: sizing, weight and alignment

Use a coherent SVG family and make each icon earn its place. Do not substitute emoji or text glyphs. Separate the icon artwork from its interactive target: a small icon can sit in a comfortably sized button without an icon background.

1. **Choose a role:** Inline icons beside 14px labels start at 16px; common toolbar and sidebar actions start at 18–20px; prominent standalone actions may start at 24px. Icons in the same group use the same artboard and apparent scale. Match the adjacent text and check the actual rendered result; these sizes are starting points, not laws.
2. **Select visual weight:** Start outline SVGs on a 24-unit viewBox at a stroke width of 1.5–1.75 units for regular 400–500 text, or 1.75–2 for semibold 600 text and stronger controls. Use a designed heavier variant for bold text rather than blindly thickening detailed paths. Thin and very heavy variants need special care: at small sizes thin lines can disappear and heavy lines can close gaps. Keep the same cap, join, style and perceived weight within a group; adjust optically, not by a universal formula.
3. **Lay out the group:** Align equal target boxes by their center line; use flex or grid and center each SVG within its box. Start with 40px square desktop targets, 4px between adjacent icon buttons, 16–20px artwork and 44px targets for touch. For icon plus text, begin with a 6–8px gap. Separate unrelated groups by 12–16px. Measure spacing between target boxes, not just visible strokes; account for SVG viewBox whitespace and optical weight before adjusting.
4. **Verify:** Check at actual size and 200% zoom, with mixed-shaped icons, long labels, responsive widths, hover, focus, disabled state and forced colors. Ensure icon-only controls have accessible names and real actions; hide redundant SVGs from screen readers. Required icons need appropriate contrast (generally 3:1), and text must meet text contrast requirements. Targets should satisfy [WCAG 2.2 target-size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum) (24px with exceptions); larger targets are easier to use.

These are project defaults informed by [Carbon's icon guidance](https://www.carbondesignsystem.com/building-blocks/foundations/icons/guidelines), [Atlassian's icon usage](https://atlassian.design/components/icon/usage), and [Apple's weight and alignment guidance](https://developer.apple.com/videos/play/wwdc2021/10097/). The sources support consistent size, alignment and optical weight; they do not prescribe the stroke and gap values above for every product.

## Disclosure and directional indicators

- Use a chevron only when it explains an actual disclosure or selection. Remove arrows on static dates, headings, and buttons with no expandable content. A directional navigation button may use a direction icon when it performs that navigation.
- Do not use text glyphs such as ⌄, ‹ or › for UI arrows: font metrics, baselines and weights vary. Use a consistent inline SVG with a square viewBox, no icon background, currentColor stroke, and decorative aria-hidden; start at 16 × 16 CSS px with a 1.5–2 px stroke, rounded ends and joins. Keep icons non-shrinking, centered in their box, and visually centered with the label using inline-flex/flex and align-items: center. Start with an 8 px label-to-icon gap; adjust optically for the typeface and check at zoom.
- For a disclosure, use a real button with an accessible name and aria-expanded synchronized with the actual open state; add aria-controls when it identifies the controlled panel. Enter and Space must activate it. For a custom select or menu use the appropriate accessible interaction pattern and keyboard handling, rather than applying disclosure semantics blindly.
- Start a downward chevron closed and rotate 180 degrees on expansion, or use right/down for a nested disclosure; use the same mapping consistently. Animate only the icon transform, roughly 120–180 ms ease-out, and remove motion under prefers-reduced-motion. Avoid moving the label or delaying focus feedback. For non-expanding previous/next controls, use correctly directed SVGs and explicit accessible names; do not rotate them as if they were disclosures.
- Check alignment, legibility, contrast, open/closed state, pointer and keyboard operation, zoom, disabled states, and reduced-motion behavior. Required graphical indicators need 3:1 contrast against their adjacent background; text labels retain their text contrast requirements.

References: [W3C disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/), [W3C accordion pattern](https://www.w3.org/WAI/ARIA/apg/patterns/accordion/), and [WCAG 2.2](https://www.w3.org/TR/WCAG22/). Dimensions and animation timing are implementation starting points, not W3C mandates.
